1. Tech Stack
Monorepo layout: root package.json orchestrates backend/ and frontend/ via concurrently (no Turborepo/Nx — just npm scripts: predev runs scripts/bootstrap-dev.mjs, dev/build/start run both sides in parallel).

Backend (backend/package.json, name @ar-company/backend):

Node.js + Express 4 (express)
Language: TypeScript (ESM, "type": "module"), run via tsx watch src/server.ts in dev, compiled with tsc for prod (dist/backend/src/server.js)
No ORM — raw pg (node-postgres) driver wrapped in a hand-built MongoDB-like collection abstraction (backend/src/db/postgres.ts) exposing find/findOne/insertOne/updateOne/deleteOne/aggregate over Postgres tables, with automatic camelCase↔snake_case mapping and dynamic column introspection via information_schema.columns
Database: PostgreSQL (targeted at Supabase — db/postgres.ts reads SUPABASE_DB_URL/DATABASE_URL/POSTGRES_URL env vars, auto-enables SSL for supabase.co hosts)
Auth: jsonwebtoken (JWT) + bcryptjs for password hashing
Validation: zod
Testing: jest + supertest, ts-jest/tsx-based
CORS: cors package with explicit allow-list + dev bypass
Frontend (frontend/package.json, name my-v0-project — built with v0.dev):

Next.js 16 (App Router, frontend/app/), React 19
Styling: Tailwind CSS 4 + tailwindcss-animate/tw-animate-css
UI kit: Radix UI primitives + shadcn/ui-style components (frontend/components/ui/*), lucide-react icons, cmdk, vaul, sonner (toasts), framer-motion
Data/forms: @tanstack/react-query, @tanstack/react-table, react-hook-form + @hookform/resolvers + zod
Charts: recharts
Routing note: wouter is a dependency (lightweight router), though primary routing is Next.js App Router; wouter may be used for the public marketing pages under frontend/pages/*
E2E testing: Playwright (@playwright/test, scripts e2e, e2e:ui, e2e:headed, e2e:debug)
Deployed to Vercel (@vercel/analytics, root vercel.json)
Shared code: shared/types/index.ts — a single shared TypeScript types file (compiled to .js/.d.ts) imported by both backend (../../../shared/types/index.js) and frontend (@shared/types). This is the canonical domain model / DTO contract.

No Prisma, no Nest, no GraphQL — it's a straightforward Express REST API + Next.js frontend with a custom Postgres data-access layer mimicking MongoDB semantics.

The system runs on a backend-tolerant-of-missing-tables design: db/postgres.ts catches Postgres error code 42P01 (undefined table) and returns empty results instead of crashing — this is a deliberate resilience pattern noted in missing.md, meaning many "modules" can be enabled UI-first before their tables exist.

7. Auth & Roles
Mechanism: Stateless JWT (jsonwebtoken), 12-hour expiry, signed with JWT_SECRET env var (falls back to an insecure dev secret with a console warning; throws in production if unset). Login endpoint: POST /api/users/auth/login (rate-limited via rateLimitLogin), password verified with bcryptjs.

Request auth flow (backend/src/middleware/auth.ts):

requireAuth middleware runs globally on every request except an explicit public-path allowlist: /api/health, /api/users/auth/login, /api/public/site-content, /api/it-admin/maintenance-state (GET, so admins can recover from lockout), and POST /api/feedback (public admissions form submissions).
Verifies Authorization: Bearer <token>, decodes JWT payload into req.auth (AuthContext), and computes effectivePermissions by merging the role's base permission set + any secondaryRoles + per-user permissions overrides (AuthTokenPayload.permissions allows individual grant/revoke).
enforceMaintenanceMode middleware then checks the maintenance_state table; if enabled, blocks all non-exempt roles with HTTP 503 (admin/super-admin/it-admin are exempt). Tolerates the table not existing yet (42P01) by skipping enforcement.
Authorization helpers: requireAdmin (admin/super-admin/supervisor only), requirePermission(...perms) (admin/super-admin bypass; others must have all listed permissions in effectivePermissions).

Roles (SystemRole type in shared/types/index.ts, 20 values): admin, super-admin, supervisor, user, student, professor, advisor, teaching-assistant, registrar, admissions, finance, it-admin, dean, hod, librarian, student-affairs, hr, security, facilities, research-office.

Each role has a hardcoded permission array in rolePermissions (middleware/auth.ts), e.g.:

admin/super-admin: near-full permission set (manage_users, students/professors/finance/enrollment/feedback/news/audit/reports CRUD+approve, ADMIN_VIEW_SCHEDULE, MANAGE_RESOURCES, settings incl. security/integrations/sso)
student: enrollment:self only
professor: ENTER_GRADES, edit_own_grades
finance: finance:view/manage/approve, VIEW_FINANCIALS, reports:view/export
registrar: user create/edit, student create/edit, enrollment manage, edit_any_grade, ADMIN_VIEW_SCHEDULE, MANAGE_RESOURCES
Granular per-role permission lists exist for all 20 roles.
Permission model is a flat string-union type Permission (referenced from shared/types) covering resource-scoped actions like students:view/create/edit/delete, finance:view/manage/approve, enrollment:view/manage/self/override-window/override-capacity, audit:view/export, settings:manage/security/integrations/sso, plus some legacy uppercase constants (VIEW_FINANCIALS, ADMIN_VIEW_SCHEDULE, MANAGE_RESOURCES, override_capacity, edit_any_grade, ENTER_GRADES, edit_own_grades) — suggesting the permission system evolved incrementally and mixes two naming conventions.

Frontend auth: frontend/lib/auth-context.tsx — React Context (AuthProvider) storing AuthUser (id, username, displayName, email, role, secondaryRoles, avatarUrl, studentId/professorId, permissions, customRoleId/Name, accessProfile), exposing login/logout/updatePassword/adminResetPassword/fetchUserNotifications/updateProfile/hasPermission/effectivePermissions/isAdmin/isStudent. Talks to backend via /api (proxied through frontend/app/api/[...path]/route.ts, a Next.js catch-all route handler) or directly via NEXT_PUBLIC_API_URL if set. Route protection enforced client-side via frontend/components/dashboard-route-guard.tsx, gating each /dashboard/<role> and /student/* route tree.

Custom roles: users.ts also exposes /custom-roles CRUD, and User/CustomRoleTemplate types support a baseRole + per-permission override + AccessProfile (fine-grained boolean flags like allowEnrollmentAnytime, allowFinanceApprovals, allowAuditExports, etc.) — an extensibility layer beyond the fixed 20 roles.
